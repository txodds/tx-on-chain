The repository includes runnable devnet scripts under [`examples/devnet`](https://github.com/txodds/tx-on-chain/tree/main/examples/devnet). They exercise the current activation, booking, streaming, fixture validation, and V4 odds and stat validation flows against `https://txline-dev.txodds.com`.

<Info>
The scripts use the devnet IDL and generated types in `examples/devnet/idl/txoracle.json` and `examples/devnet/types/txoracle.ts`. For mainnet integrations, use the root `idl/txoracle.json` and `types/txoracle.ts`, or the mainnet scripts under `examples/mainnet`.
</Info>

## Requirements

- Node.js `20` or newer. The current lockfile resolves `eventsource@4.1.0`, which declares `node >=20.0.0`.
- A devnet wallet keypair file for `ANCHOR_WALLET`, funded with devnet SOL for transaction fees.
- `ANCHOR_PROVIDER_URL="https://api.devnet.solana.com"`.
- `TOKEN_MINT_ADDRESS=4Zao8ocPhmMgq7PdsYWyxvqySMGx7xb9cMftPMkEokRG`.

Install dependencies from the repository root:

```bash
yarn install
```

Run every script from the repository root with the devnet environment values:

```bash
TOKEN_MINT_ADDRESS=4Zao8ocPhmMgq7PdsYWyxvqySMGx7xb9cMftPMkEokRG \
ANCHOR_PROVIDER_URL="https://api.devnet.solana.com" \
ANCHOR_WALLET="./_keys/testuser-wallet-1.json" \
yarn ts-node examples/devnet/scripts/subscription_free_tier.ts
```

Each script's header comment has the exact command for that script.

## Recommended Order

A fixture must be booked before its data can be validated on-chain, so run the scripts in this order on a fresh wallet:

<Steps>
  <Step title="Fund the wallet with mock USDT">
    `request_devnet_usdt.ts` requests mock USDT from the program's devnet faucet.
  </Step>
  <Step title="Buy TxL">
    `purchase_tokens_usdt.ts` buys TxL with USDT through a backend-signed quote. Booking is paid in TxL.
  </Step>
  <Step title="Subscribe and fetch data">
    `subscription_free_tier.ts` subscribes, activates an API token, and fetches fixtures and odds. `show_pricing_matrix.ts` prints the service levels you can subscribe to.
  </Step>
  <Step title="Book a fixture">
    `book_fixture.ts` lists bookable fixtures, requests a quote, and books one fixture. It skips booking when the wallet already holds the ticket.
  </Step>
  <Step title="Validate on-chain">
    `V1_stat_validation_v4.ts` and `V1_odds_validation_v4.ts` run the V4 validation sequence against a booked fixture. Both book the fixture first if the wallet has no ticket for it.
  </Step>
</Steps>

`fixture_validation_view_only.ts` and `historical_scores.ts` subscribe on their own and need no booking, so they can run at any point.

</Note>

### Choosing Fixtures

- **`V1_odds_validation_v4.ts`** only picks odds updates for fixtures listed by `GET /api/fixtures-schedule` in the NFL or the Premier League. Edit the `allowedCompetitionIds` set in the script to target other bookable competitions.
- **`V1_stat_validation_v4.ts`** validates a fixture ID set in the script. Change it to a fixture from `GET /api/fixtures-schedule`. The strategies labelled "calibrated" expect particular stat values, so they return `false` on other fixtures. A confirmed transaction returns `false` when the predicate does not hold and also when the proof does not match the published root.
- **`book_fixture.ts`** books the fixture in `FIXTURE_ID`, or a default set in the script.

The shared helpers are in `examples/devnet/common`:

| File | Purpose |
|------|---------|
| `config.ts` | Devnet API and guest JWT hosts. |
| `users.ts` | Wallet setup, subscription, activation signing, JWT renewal, API client setup, and transaction safety helpers. |
| `utils.ts` | IDL-driven encoders that format API payloads into the program's argument types. |

## Validation Paths

| API request | On-chain method | Use case |
|-------------|-----------------|----------|
| `/scores/stat-validation-v4?fixtureId=...&seq=...&statKeys=1,2,...` | `validateFixtureForTree` → `validateStatV4` → `closeWorkerTicket` | Backend-co-signed multiproof validation with a `strategy`. Requires a `fixture_ticket` from `book_fixture`. |
| `/odds/validation-v4?messageId=...&ts=...` | `validateFixtureForTree` → `validateOddsV4` → `closeWorkerTicket` | Backend-co-signed validation of one odds update. Requires a `fixture_ticket` from `book_fixture`. |
| `/fixtures/validation?fixtureId=...&timestamp=...` | `validateFixture` (simulated view) | Fixture proof validation. No booking needed. |

<Warning>
The fixed fixture IDs in the example scripts are demo fixtures. In production, derive `fixtureId`, `seq`, phase, and status from an observed score record from snapshot, updates, historical data, or the scores stream, and book the fixture before validating.
</Warning>

## Final Outcome and Fixtures

On the current devnet and mainnet releases, final scores records use `action=game_finalised` with `statusId=100` and `period=100`. Use those records when validating or settling the final match outcome, regardless of whether the match ended after regulation time, extra time, penalties, or abandonment.

Fixture payloads include a backward-compatible `GameState` field. Current values are:

| GameState | Meaning |
|-----------|---------|
| `1` | Scheduled |
| `6` | Cancelled |

Use `fixture_validation_view_only.ts` for the runnable fixture proof flow. The script demonstrates fetching fixture validation data, deriving the ten-day fixture roots PDA, and simulating `validateFixture`.
